# GetLiveAward

`GetLiveAward` 是一个用于抢 Bilibili 直播奖励的桌面工具，支持扫码登录、多链接并发、自动重登和日志记录。


## 项目介绍

适用于b站任意游戏的直播创作激励领取，输入活动链接后即可自动执行抢奖流程。

## 使用方法

1. 在 Bilibili 复制奖励活动链接（注意是在领取界面的链接）

   <img width="240" height="250" alt="图片" src="https://github.com/user-attachments/assets/812aad20-a07f-4f70-a20f-cd4ea5128653"/>

2. 打开release下载的 `getLiveAward`

3. 粘贴一条或多条链接 

4. 首次使用先点击“先登录”，需要时用 B 站 App 扫码并确认；这一步不会提交领取。

5. 按活动公布的开放时间，在即将开始时点击“全部开始”，等待结果。

启动时会显示四步简短教程，说明领取链接、账号与扫码、定时 / 抖动设置和结果查看。可跳过、勾选“下次启动不再自动显示”，或通过“使用教程”随时重看。教程偏好保存在 `data/ui.ini`；启动和浏览教程不会发送网络请求。

程序会创建 `data/` 用于保存 Cookie 和日志。

## 账号管理

- 顶部点击「添加账号」，输入账号备注后自动进入扫码登录；请先在 B 站 App 切换到对应账号，再扫描并确认。添加账号只登录，不提交领取；取消扫码后可通过「先登录」重试。
- 首次直接点击「先登录」即可自动建档，无需预先添加账号。登录验证成功后，「默认账号」自动显示 B 站昵称与 UID；使用验证接口已有的返回信息，不额外请求。已有 Cookie 的账号在验证通过后同样补全身份。
- 使用账号下拉框切换，空闲时才允许添加或切换；当前输入的领取链接保留，切换后需要手动开始。新增账号的备注由用户填写；登录验证后自动保存 UID 和昵称，但不自动合并重复扫码的账号档案。
- 原有登录保留在「默认账号」中，仍使用原来的 `data/bilibili_cookie.json`、日志及设置；新增账号的 Cookie、日志和 `ui.ini` 分别保存在 `data/accounts/<账号ID>/`。`data/accounts.json` 仅保存账号 ID 和备注，记录本身不含 Cookie。
- 采用程序内账号档案，无需复制 EXE 或开多个窗口。每次只运行当前账号，便于统一管理和避免误并发；不同账号仍共享本机 IP，单独开 EXE 也不会隔离 IP 风控。本版本不提供多账号同时领取。

## 从源码运行

需要 Python 3.10 或以上版本（建议 Python 3.12）。

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python app.py
```

源码运行时，`data/` 位于项目目录；打包运行时位于可执行文件所在目录。

## 请求与并发

- 同批次共享登录结果和 WBI 密钥；密钥缓存 1 小时，签名被拒绝后最多刷新重试一次。
- 默认只允许一个奖励 API 请求在途，按输入顺序逐条执行链接；前一条结束或取消后才开始下一条。每个线程使用独立 HTTP Session 复用连接。
- 右侧设置面板支持间隔（100–60000 ms，默认 1000 ms）、超时（默认 10000 ms）、尝试次数（默认 120 次）、执行时长（默认 5 分钟）或持续运行。默认选择按次数，次数包含首次提交，开启并发时按每个领取线程计算。
- 间隔同时约束全批次请求起始间隔与每次失败后的等待；实际还会加上网络耗时。时间模式按每条链接从领取阶段计时，含暂停、重试、重新登录等待，不含初次扫码与准备；到时停止新请求，在途请求返回后退出。
- 「启用请求并发」和「同时处理多条链接」默认关闭；手动启用后，请求并发上限、同时链接数均可调到 1–4，全局请求并发上限不会因多链接而成倍放大。并发关闭时，所有链接和请求均串行。
- 这些是程序默认值，不代表 B 站公布或保证的安全频率。登录二维码按 1.5 秒间隔轮询。
- 遇到 HTTP 412/429、接口风控码 -352/-412/-509 或明确的 IP 访问异常 / 请求过于频繁提示，停止本批次后续奖励 API 请求；此保护不能关闭。网络故障采用退避重试，最长基础退避为 8 秒。
- 暂停和取消可打断排队、重试和暂停等待。在途网络请求需要返回或超时后才能结束；退出窗口会等待后台线程收尾。
- 领取成功但缺少兑换码时停止重复提交，提示人工核对；并发请求中已有成功结果会优先保留。
- 接口返回 `202032`（无资格领取奖励）时按正常间隔继续重试，兼容开放时间点资格尚未刷新的情况；受所选次数 / 时长与请求间隔约束。库存停止开关只判断领取接口明确的库存耗尽文本，不把任务查询的库存提示或 202032 当作资格已永久失效。
- 运行时锁定设置；当前批次使用启动时的设置快照。设置保存在 `data/ui.ini`，可恢复默认；「全部停止」可取消当前与排队任务。
- 界面最多保留 2000 行日志，磁盘日志按 1 MiB 轮转并保留 3 份备份。

## 抖动、校时与定时

- 「随机间隔抖动」默认关闭，额外范围默认 200 ms。开启后，每次领取失败重试前，在基础间隔上增加 0 到所设值的随机等待；不缩短基础间隔，也不作用于首次领取。这只是随机化间隔，不保证规避风控。
- 「启用时间同步」默认关闭，NTP 服务器默认 `ntp.aliyun.com`。只校准程序内部时间及签名时间戳，不修改 Windows 系统时间。日志显示时间偏差和往返耗时。
- 执行方式选择「定时执行」后，默认目标为下一次北京时间 `00:00:00`，首发延迟默认 100 ms，可调 0–60000 ms；例如默认客户端目标为 `00:00:00.100`。这是一次性任务，不会每日自动重复。
- 定时模式强制启用校时，默认每 60 秒校时，可调 5–3600 秒。首次校时失败不会开始任务；后续偶发失败暂用上次样本，超过有效期则中止，不静默退回未校准时间。
- 点击「全部开始」后先完成首批链接的登录、任务信息准备，再等待目标时间；默认只准备第一条，其余链接仍按队列执行。长时间等待时，临近目标前会刷新登录与 WBI，避免首发时临时获取密钥。等待不提交领取；临近目标最后 2.5 秒不再发起新的 NTP 查询。
- 「到点后」可选按次数、按时长或持续运行；次数和时长从领取阶段计算，不消耗在定时等待期间。抖动只影响后续重试，100 ms 首发延迟单独生效。
- 请提前扫码并保持程序运行、电脑唤醒和联网。系统调度、网络握手、在途请求和准备过晚均可能导致实际发送晚于目标；100 ms 是客户端目标延迟，不能保证服务器在该时刻收到请求。已有请求间隔和风控保护仍然生效。
